This project uses TypeScript, Vue, Nuxt, and Supabase. If you know Python, this page maps every one of those concepts onto something you already know. Read it once; everything else in the docs will make more sense.

## The language: TypeScript

TypeScript (TS) is JavaScript plus type annotations. Think of it as Python with `mypy --strict` always on - the types are checked at build time and erased at runtime.

| Python | TypeScript | Notes |
|---|---|---|
| `def f(x: int) -> str:` | `function f(x: number): string` | Same idea |
| `dict[str, Any]` | `Record<string, unknown>` | |
| `Optional[str]` / `str \| None` | `string \| null` or `string \| undefined` | JS has **two** "nothing" values; `undefined` = never set, `null` = deliberately empty |
| `dataclass` / `TypedDict` | `interface` | `interface DbJob { id: string; ... }` - purely a type, no runtime cost |
| `list[int]` | `number[]` or `Array<number>` | |
| f-string `f"{x}s"` | template literal `` `${x}s` `` | Backticks, not quotes |
| `**kwargs` spread | `{ ...obj }` spread | `{ ...defaults, ...overrides }` merges dicts |
| `lambda x: x + 1` | `(x) => x + 1` | "Arrow function" |
| `import x from y` | `import { x } from './y'` | Named imports use `{}`; `export default` imports without |
| `if x is None:` | `if (x == null)` or `x ?? fallback` | `??` is "use fallback if null/undefined" |
| `a.b if a else None` | `a?.b` | Optional chaining - safe attribute access |

Three TS-isms you'll see everywhere in this codebase:

- **`const` everywhere** - like never reassigning a variable. `let` allows reassignment; `const` doesn't (but object *contents* can still change).
- **`x!`** - "trust me, this is not null". Used after a bounds check. Overusing it causes crashes; this project's `tsconfig` has `noUncheckedIndexedAccess: true`, meaning `array[i]` is typed `T | undefined` and you *must* handle the undefined case (see [common-pitfalls.md](/guides/common-pitfalls)).
- **`as SomeType`** - a cast, like `typing.cast`. No runtime check; it just tells the compiler to believe you. Job `input` fields are casted this way because they're stored as untyped JSON.

## Async: the single biggest difference

Python usually blocks: `requests.get(...)` waits. JavaScript **never blocks** - everything I/O-shaped returns a `Promise` (exactly Python's `asyncio` `Future`/coroutine, but it's the *only* model, there's no sync alternative).

```ts
// TypeScript                            # Python asyncio equivalent
async function load(): Promise<Data> {   # async def load() -> Data:
  const res = await $fetch('/api/x')     #     res = await client.get('/api/x')
  return res                             #     return res
}

await Promise.all([a(), b()])            # await asyncio.gather(a(), b())
await Promise.allSettled([...])          # gather(..., return_exceptions=True)
setInterval(fn, 2000)                    # loop.call_later-style repeating timer (every 2s)
setTimeout(fn, 2000)                     # loop.call_later(2, fn) (once)
```

There's one thread. Long CPU work freezes everything - that's why slow work (AI generation, ffmpeg) lives in the separate **worker process**, not in an HTTP handler.

## The runtime split: browser vs server

This one has no Python equivalent, and it explains the whole folder layout:

- Code in **`server/`** runs in **Node.js** on your machine/server. It can read files, spawn ffmpeg, hold secrets. Like a Flask/FastAPI app.
- Code in **`app/`** runs in the **user's browser** (mostly). It cannot keep secrets - anything in it is visible to the user. It talks to the server via HTTP (`$fetch('/api/...')`).
- Code in **`shared/`** is imported by *both* sides, so it must be pure logic with no secrets and no Node-only APIs (e.g. `scriptLength.ts` word-count math).

Nuxt also renders pages on the server first (SSR - server-side rendering) then "hydrates" them in the browser, but you rarely need to think about that here.

## Vue in 60 seconds

A `.vue` file is one **component**: a chunk of UI with its own logic. It has up to three blocks:

```vue
<template>   <!-- HTML with {{ interpolation }} and directives -->
  <button :disabled="loading" @click="save">{{ label }}</button>
</template>

<script setup lang="ts">   <!-- the component's logic (runs once per component instance) -->
const loading = ref(false)          // reactive value - like a observable variable
const label = computed(() => loading.value ? 'Saving…' : 'Save')  // derived value, auto-recomputes
async function save() { ... }
</script>

<style scoped> /* CSS that only applies to this component (rare here - Tailwind is used instead) */ </style>
```

Key reactivity concepts (this is Vue's whole trick):

- **`ref(x)`** - wraps a value so Vue notices changes. Read/write via `.value` in scripts (`loading.value = true`), but *without* `.value` in templates. Think of it as a property with change-notification, like C#'s `INotifyPropertyChanged`.
- **`computed(fn)`** - cached derived value that recomputes automatically when its inputs change. Like a spreadsheet cell.
- **`watch(source, fn)`** - run a callback when a reactive value changes. Used a lot here to react to job status flipping to `completed`.
- **props** - inputs a parent passes to a child component (like function kwargs): `defineProps<{ projectId: string }>()`.
- **emits** - events a child sends up to its parent: `emit('done')`. Parent listens with `@done="handler"`. Data flows **down via props, up via emits** - children never modify parent data directly.
- **`v-if` / `v-for` / `:x` / `@x`** in templates - conditional render / loop / bind attribute to expression / attach event listener.

Component naming: Nuxt auto-imports components from `app/components/` by their path - `app/components/stages/ScriptStage.vue` is used in templates as `<StagesScriptStage>`. Nothing needs importing manually.

## Nuxt in 60 seconds

Nuxt is the framework gluing everything together (think Django, where Vue alone would be Jinja). Its big features used here:

- **File-based routing** - `app/pages/dashboard.vue` *is* the route `/dashboard`. `app/pages/workspace/[projectId].vue` is `/workspace/:projectId` (brackets = URL parameter, like FastAPI's `/workspace/{project_id}`).
- **File-based API** - `server/api/projects/index.get.ts` *is* `GET /api/projects`. The HTTP method is in the filename: `.get.ts`, `.post.ts`, `.patch.ts`, `.delete.ts`. `[id].get.ts` = path parameter.
- **Auto-imports** - `ref`, `computed`, `useRoute`, all composables in `app/composables/`, and helpers like `defineEventHandler`, `readBody`, `createError` in server routes are available without import statements. If you see an unimported function, it's auto-imported - don't add an import.
- **Layouts** (`app/layouts/`) - shared page chrome (nav bars). A page opts in via `definePageMeta({ layout: 'dashboard' })`.
- **Middleware** (`app/middleware/auth.ts`) - runs before entering a route; here it redirects logged-out users to `/auth/login`. Like a Django login-required decorator.
- **`$fetch`** - Nuxt's built-in HTTP client (like `httpx`). `await $fetch('/api/jobs', { method: 'POST', body: {...} })`.
- **Nitro** - Nuxt's server engine (the part that runs `server/`). You'll see the name in `nuxt.config.ts` and "Nitro plugin" (`server/plugins/worker.ts` - code that runs once at server startup).

## Pinia (state management)

Pinia stores are app-wide singletons holding shared state - like a module-level object in Python, but reactive. Defined in `app/stores/`, used from any component:

```ts
const projectStore = useProjectStore()   // same instance everywhere
projectStore.loadProject(id)             // actions are just methods
projectStore.currentStage                // reactive state
```

Rule of thumb in this project: state needed by **many components** lives in a store (current project, job map); state owned by **one stage** lives in a composable (see below).

## Composables

A composable is a plain function starting with `use...` that bundles reactive state + functions, for reuse across components - like a Python mixin or a small class factory. `useScenes(projectId)` returns `{ scenes, fetchScenes, updateScene, ... }`. Each *call* creates fresh state (unlike stores, which are singletons).

## Supabase

Supabase = hosted Postgres + authentication + file storage, accessed via a client library instead of raw SQL:

```ts
const { data, error } = await supabase
  .from('jobs')                  # SELECT * FROM jobs
  .select('*')
  .eq('project_id', projectId)   # WHERE project_id = $1
  .order('created_at', { ascending: false })
```

Errors are returned as values, not raised - always check `error` (like Go).

Two client flavors in this project - **this distinction matters for security**:

| Client | Where | Permissions |
|---|---|---|
| `serverSupabaseClient(event)` (from `supabase-server.ts`) | API routes | Acts **as the logged-in user**; Postgres Row-Level Security (RLS) automatically restricts rows to what that user owns |
| `adminSupabase` (from `server/worker/lib/supabase.ts`) | Worker + a few routes | **Service role - bypasses RLS entirely.** Only use after ownership is verified another way |

**RLS (Row-Level Security)** = WHERE clauses enforced by the database itself per table (defined in the migrations). Even buggy API code can't leak another user's rows when using the user client.

## Tailwind CSS

Instead of CSS files, styling is done with utility classes directly in templates: `class="px-4 py-2 text-sm text-gray-400 rounded-lg"` = padding-x 1rem, padding-y 0.5rem, small text, gray, rounded corners. You can read them left to right; the [Tailwind docs](https://tailwindcss.com/docs) are a lookup table. This project uses Tailwind v4 (configured via `@tailwindcss/vite` in `nuxt.config.ts`, no `tailwind.config` file).
