- Project: Vira Project

Source card: [User Flow Rework: Script → Audio → Image → Video](https://app.superthread.com/strawberry-tech/card-109-user-flow-rework-script--audio--image--video)

**Overview**

Change pipeline stage order from Script → Image → Audio → Video to Script → Audio → Image → Video. Audio must run before image and video so `scenes.duration` is populated from real ffprobe data before video generation jobs are submitted.

**Why this order matters**

Audio generation via ffprobe sets the real duration of each scene. Video providers need an integer duration. Running audio first means every video generation job gets an accurate, verified duration  -  not an estimate.

**Scope**

- Update stage order in the workspace navbar UI

- Audit `workspace.ts` Pinia store  -  update stage gating logic (do NOT only change the navbar)

- Audit all components that read stage completion state and use it to gate the next stage

- Confirm AudioStage feeds `scenes.duration` before ImageStage and VideoStage unlock

- Run all existing export handler integration tests after the change

- Manual end-to-end test of the full pipeline in the new order

**Notes**

This is primarily a store and navbar change but the gating logic in `workspace.ts` must be audited thoroughly. Do not assume it is just a UI reorder.

#### Script Length Guard (3m Maximum)

- Status: `completed`
- Priority: P2
- Estimate: 2
- Tags: Short form
- Project: Vira Project

Source card: [Script Length Guard (3m Maximum)](https://app.superthread.com/strawberry-tech/card-104-script-length-guard-3m-maximum)

**Overview**

Prevent users from generating scripts that would produce more than the selected target length (default 3 minutes / 180s). Enforce in two layers: LLM system prompt instruction and a validation check before scene split proceeds. Respects the user-selected length from the Script-phase length selector.

**Scope**

- Add instruction to all script generation LLM system prompts: target the selected length at natural speaking pace (~130 words per minute). Default target 180s (~390 words); hard ceiling 3m.
- After script generation, run a word count check on the output.
- Estimated duration formula: `word_count / 130 * 60` seconds.
- If estimated duration exceeds the selected target: surface a warning with option to regenerate or manually trim.
- Hard block scene split if script is significantly over the 3m ceiling (>210s estimated).

**Notes**

Changed from 60s to 3m to match the pivot (YouTube Shorts now allow up to 3 minutes). This is a rough guard  -  the real duration is set by ffprobe after audio generation. The purpose is to stop obviously oversized scripts from entering the pipeline, not to be a precise length enforcer. Pairs with the new "Video Length Selector (Script Phase)" card.

#### Redis + SSE Push Model (Replace 3s Polling)

- Status: `Infrastructure & Docs`
- Priority: P1
- Estimate: 4
- Tags: Infrastructure
- Project: Vira Project

Source card: [Redis + SSE Push Model (Replace 3s Polling)](https://app.superthread.com/strawberry-tech/card-128-redis--sse-push-model-replace-3s-polling)

**Overview**

Replace the current 3-second polling model with a Redis-backed push system using Server-Sent Events (SSE). Job completion updates are pushed to the client in real time instead of the client checking every 3 seconds.

**Why it's backlog**

The current 3-second polling works. It is not elegant and it does not scale to thousands of concurrent users  -  but you do not have thousands of concurrent users. Adding Redis and SSE infrastructure before you have the load that requires it is premature optimisation.

**When to build**

- Production monitoring shows polling creating measurable DB or server load
- 200+ concurrent active users generating jobs simultaneously
- Polling has been confirmed as the actual bottleneck, not something else

**Implementation notes**

- Upstash Redis (already used for rate limiting) can be extended for pub/sub without a new service
- SSE is simpler than WebSockets for unidirectional job status updates
- Worker publishes to a Redis channel on each job status change
- Nuxt server route subscribes and streams updates to the client via SSE

**Checklist**

_Implementation Steps_

- [ ] Update all 8 worker handlers to publish a job status event to the user's Redis channel on every status change (pending → running → completed/failed)
- [ ] Extend Upstash Redis (already used for rate limiting) for pub/sub: create a per-user job status channel pattern
- [ ] Add SSE reconnection logic: if connection drops, re-establish automatically with exponential backoff (1s, 2s, 4s, max 30s)
- [ ] Write tests for SSE event emission from worker and receipt in the composable
- [ ] Create Nuxt SSE endpoint at GET /api/jobs/stream: authenticates user, subscribes to their Redis channel, streams events to client
- [ ] Keep 3s polling as a silent fallback: if SSE fails to reconnect after 3 attempts, fall back to polling without user-visible interruption
- [ ] Confirm production monitoring shows polling is a measurable bottleneck  -  do not start this task without data proving the problem exists
- [ ] Load test: simulate 100+ concurrent users with active generation jobs and confirm DB polling load has been eliminated
- [ ] Update useJobPoller composable: replace 3-second setInterval with an SSE EventSource listener that updates job state on push events

#### Self-Hosted Supabase

- Status: `Infrastructure & Docs`
- Priority: P1
- Estimate: 4
- Tags: Infrastructure
- Project: Vira Project

Source card: [Self-Hosted Supabase](https://app.superthread.com/strawberry-tech/card-129-self-hosted-supabase)

**Overview**

Migrate from Supabase managed cloud to a self-hosted Supabase instance for full infrastructure control, data sovereignty, and cost reduction at scale.

**Why it's backlog**

Supabase managed cloud works, requires zero DevOps overhead, and has generous free tiers. Self-hosting adds significant complexity  -  Docker, PostgreSQL management, backup strategy, storage configuration, auth configuration  -  with zero user-facing benefit at current scale.

**When to build**

- Monthly Supabase managed cloud cost exceeds the engineering cost of owning the infrastructure

- A specific data sovereignty or compliance requirement from an enterprise customer

- Engineering capacity available to own and maintain the infrastructure reliably

**Notes**

Do not conflate self-hosting with data control. RLS policies already enforce complete row-level data isolation on managed cloud. Self-hosting is a cost and sovereignty decision, not a security one.

**Checklist**

_Implementation Steps_

- [ ] Re-apply all RLS policies on the self-hosted instance and verify they enforce correctly with test queries
- [ ] Run a full end-to-end pipeline test against the self-hosted instance in a staging environment  -  confirm all 29 API routes, auth, storage, and Realtime work correctly
- [ ] Install Docker and Docker Compose on the target server and verify they are running correctly
- [ ] Clone the Supabase self-hosted repository and configure docker-compose.yml with the correct service versions
- [ ] Provision a VPS with sufficient resources: minimum 4GB RAM, 2 vCPUs, 50GB SSD for Postgres + Supabase service stack
- [ ] Set up automated daily DB backups: pg_dump to an external object storage bucket (S3 or Cloudflare R2) with 30-day retention
- [ ] Start the full Supabase stack and confirm all services are healthy: Studio, Auth, Storage, Realtime, PostgREST, Kong API gateway
- [ ] Cut over production traffic to self-hosted instance  -  monitor error rates, latency, and storage performance for 48 hours before decommissioning managed cloud
- [ ] Configure all required environment variables: DB password, JWT secret, anon key, service role key, site URL, SMTP settings
- [ ] Import schema and data into self-hosted Postgres and run all 5 existing migrations  -  verify row counts match managed cloud
- [ ] Migrate storage assets: copy all files from the managed cloud assets bucket to the self-hosted storage service
- [ ] Export production DB schema and all data from managed cloud using pg_dump
- [ ] Set up uptime monitoring and alerting for all self-hosted services  -  alert on any service going down within 2 minutes
- [ ] Update all application environment variables (Vercel + Fly.io) to point to the self-hosted Supabase URL and new API keys
- [ ] Confirm managed cloud costs justify the migration: calculate current monthly Supabase bill vs estimated self-hosting infrastructure + engineering overhead
