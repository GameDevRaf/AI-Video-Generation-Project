# Planned: Retry, Usage Logging, Team Access

> Implementation guidance for job retry (98), usage logging (134), and team provider access (136), plus light notes for 99, 121, 122.

This page is a planning reference for future implementation work, not a description of shipped behavior. It exists so a future prompt can start implementing directly instead of re-deriving architecture context. Written during the 2026-07-04 provider audit pass; see [Provider API Audit](/backend/provider-api-audit) for the per-provider research this leans on.

## Superthread 98: Error States + Manual Job Retry

**Current state** (already true today, no changes needed for this part):

- Every adapter throws descriptive errors; `getProviderKey` already throws a user-friendly message (`No active API key found for provider "X". Add one in Settings -> API Keys.`); `processJob` in `server/worker/loop.ts` stores `err.message` verbatim into `jobs.error_message`. So human-readable error propagation from provider to DB already works.
- The frontend already reads `job.error_message` and renders it (e.g. `app/components/stages/ImageStage.vue:44,155`). There is no retry button anywhere.
- Automatic retry: up to `MAX_RETRIES = 3` (`server/worker/loop.ts`), then `status: 'failed'`. `POST /api/jobs` only dedupes `queued`/`processing` jobs (see `/backend/api-routes`), so a failed job is not reused: calling it again for the same input creates a brand-new job row.

**Gap**: no way to re-run the *same* failed job (same type/input/provider/model) without going through the stage UI's normal "generate" flow, and no UI affordance to do so.

**Recommended API**: `POST /api/jobs/:id/retry`

- Verify ownership (same pattern as other `[id]` routes).
- Guard: 400 if `job.status !== 'failed'`.
- Reset in place (do not insert a new row): `status: 'queued', retry_count: 0, error_message: null, completed_at: null, started_at: null`. Reusing the row keeps `job_outputs` history attached to one job id and matches the existing "retries re-run the whole handler, outputs are insert-only latest-wins" tolerance documented in [Job Queue and Worker](/backend/job-queue-and-worker).
- Optional body `{ provider?, model?, input?: object }` merged over the existing job before re-queuing, so a user can switch provider (e.g. after adding a key for a different one) instead of only retrying the exact same failing config. This directly helps the common "no API key" failure mode (ties into 99 below).
- Return the updated job row; the worker picks it up on its next 3s tick.

**Recommended UI**: add a `resumeJob(jobId)` (or similar) to `useJobPoller` that POSTs to the retry endpoint and resumes polling, and a "Retry" button next to the existing error text wherever `job.error_message` is shown (`ImageStage.vue`, `VideoStage.vue`, `ExportStage.vue`, `SceneSplitStage.vue`, and anywhere else stages surface `isFailed`).

**Testing strategy**:
- Unit: retry endpoint rejects non-owner, rejects non-`failed` status, correctly resets fields.
- Integration: create a job, force it to `failed` (e.g. bad key), call retry, assert the worker's next tick flips it back through the normal lifecycle.
- No e2e needed for this alone.

**Open question**: should the retry endpoint keep a record of prior failures (for card 134's usage/error analytics) before clearing `error_message`? If usage logging (134) lands first, prefer writing failure events to `usage_logs` (below) rather than growing the `jobs` table, so `jobs.error_message` can stay "latest attempt only" as it is today.

## Superthread 134: API Usage Logging + Limit Notifications

**Current state**: no usage/cost data is captured anywhere. Provider adapters return only the category result (`{ text }`, `{ imageUrl }`, `{ audioBuffer, mimeType }`, `{ videoUrl }`) - no token/character/cost metadata flows back to handlers today. See the per-provider "usage/cost metadata" notes in [Provider API Audit](/backend/provider-api-audit) for what each API actually exposes (token usage for LLMs, character counts for most TTS, per-image/per-second billing for image/video).

**Recommended schema** - new table, migration `supabase/migrations/009_usage_logs.sql`:

```sql
create table usage_logs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete cascade,
  project_id uuid references projects(id) on delete set null,
  job_id uuid references jobs(id) on delete set null,
  provider text not null,
  model text not null,
  category text not null, -- 'script' | 'image' | 'audio' | 'video'
  units jsonb not null,   -- e.g. { tokensIn, tokensOut } or { characters } or { seconds } or { images: 1 }
  estimated_cost_usd numeric,
  created_at timestamptz not null default now()
);
```

RLS: owner-only (`auth.uid() = user_id`), same pattern as every other table.

**Contract change needed**: `ScriptResult`/`ImageResult`/`AudioResult`/`VideoResult` in `server/worker/providers/types.ts` each gain an optional `usage?: Record<string, number>` field (shape per category, e.g. script: `{ tokensIn, tokensOut }`; audio: `{ characters }`; image/video: `{ units: 1 }` or duration-based). Adapters populate it from whatever the SDK/API response already includes (see audit doc per provider); adapters that can't report usage simply omit it. Handlers write a `usage_logs` row alongside the existing `storeTextOutput`/`storeFileOutput` call, using `job.provider`/`job.model`/`job.user_id`/`job.project_id`.

**Cost estimation**: maintain a separate `server/worker/providers/pricing.ts` config (cost per 1K tokens / per character / per image / per video-second, keyed by provider+model), analogous to `catalog.ts` but for pricing rather than UI metadata. Seed it with the rates found during this audit (see audit doc) but expect it to drift - treat it as a best-effort estimate, not billing-grade accounting, and say so in the UI.

**Aggregation**: given expected volume (single-tenant/small-team app), a live `SUM(...) GROUP BY date`/`project_id` query against `usage_logs` is enough - no rollup table needed initially.

**Thresholds / soft stop**:
- Add nullable `user_settings.daily_cost_limit_usd` and/or `project_settings.cost_limit_usd`.
- Cheapest correct place to enforce: `POST /api/jobs` - before inserting, sum today's `usage_logs.estimated_cost_usd` for the user (or project) and reject with a clear `402`/`429`-style error if a limit is set and already exceeded. This reuses the same "fail fast before queueing" idea as the card 99 no-key guard below - consider building both checks as one shared helper (`assertCanStartJob(userId, projectId, providerId)`).
- Notification delivery: no email/push infra exists in this codebase today. Recommend starting with an in-app usage banner (`GET /api/usage/summary?projectId=` returning today's/this-project's totals vs. limit) rather than assuming a notification channel that doesn't exist yet. Flag this as an assumption to confirm with the user before building anything beyond in-app UI.

**Testing strategy**:
- Unit: pricing math, threshold comparison logic.
- Integration: a completed job writes a correctly-shaped `usage_logs` row; job creation is blocked once a configured limit is exceeded.

**Open questions**: per-user or per-project budgets (no team/org concept exists yet - see 136)? Log usage for a provider call that succeeded even if a *later* stage of the same job fails? (Recommend: yes, log at the point the provider call returns successfully, since the cost was actually incurred regardless of overall job outcome.)

## Superthread 136: Wire Team Provider Access

**Current state**: `api_keys` is strictly per-user (`user_id` FK, owner-only RLS). There is no team/organization/workspace entity anywhere in the schema - `projects` belongs directly to a `user_id`. This is the real scope of 136: "team" doesn't exist as a concept yet, so this card is schema-first, not just a key-sharing tweak.

**Recommended schema** (flag these as decisions for the user/product to confirm, not settled):

```sql
create table teams (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  owner_user_id uuid not null references users(id),
  created_at timestamptz not null default now()
);

create table team_members (
  team_id uuid not null references teams(id) on delete cascade,
  user_id uuid not null references users(id) on delete cascade,
  role text not null default 'member', -- 'owner' | 'admin' | 'member'
  created_at timestamptz not null default now(),
  primary key (team_id, user_id)
);

create table team_api_keys (
  id uuid primary key default gen_random_uuid(),
  team_id uuid not null references teams(id) on delete cascade,
  provider text not null,        -- same "key provider id" convention as api_keys.provider
  key_name text,
  encrypted_secret text not null,
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

alter table projects add column team_id uuid references teams(id);
```

Prefer a **separate** `team_api_keys` table over adding a nullable `team_id` to the existing `api_keys` table: it avoids retrofitting RLS policies onto a table whose current policies assume `user_id` is always the owner, and keeps the blast radius of this change small.

**Key resolution order change** in `server/worker/lib/getProviderKey.ts`: when a job's project has a `team_id`, check `team_api_keys` for `keyProviderId ?? providerId` first, then fall back to the user's personal `api_keys`. This mirrors the existing cascading-default convention already used elsewhere (job input -> job row -> project_settings -> user_settings -> hardcoded default; see [Database Schema](/database/schema)), so it's consistent with how this codebase already does fallbacks.

**Encryption note**: `server/utils/crypto.ts` derives one single AES-256-GCM key application-wide from `SUPABASE_SERVICE_ROLE_KEY` (`derivedKey()`) - it is not per-user or per-tenant scoped today. That's a pre-existing property of the system, not something 136 needs to fix, but don't assume adding teams gives you per-tenant key isolation for free - all secrets (personal or team) share the same encryption exposure surface as today.

**Dual credentials**: team keys reuse the exact same "JSON blob in `encrypted_secret`" pattern already used for Kling/PlayHT - no new design needed.

**UI**: a "Team" section in Settings (create/join team, manage members, manage team keys). `ModelSelector.vue` / `ProviderPanel.vue` would need to distinguish "using team key" from "✓ key saved" (personal) so users understand provenance - both currently only check `savedProviderIds.includes(keyProviderId ?? id)`.

**Testing strategy**: unit tests for the new resolution order (team-key-first, personal-key-fallback); RLS tests for `team_api_keys`/`team_members`; integration test that a team member with no personal key can still generate using the team's key.

**Open questions to confirm before implementing**: Is there a billing/plan concept for teams decided elsewhere already? Should team keys be visible/editable by all members or admins only? Can a project mix sources (team key for provider A, personal key for provider B) simultaneously, or is it all-or-nothing per project?

## Superthread 99: No API Key Notification (light note, likely folds into 136)

Recommend implementing this **independently and now**, it's cheap and doesn't need the team schema: before a job would be created (`POST /api/jobs`) or claimed, check a key exists for `keyProviderId ?? providerId` (same lookup `getProviderKey` already does) and reject fast with the existing friendly message pattern, instead of letting the job reach `processing` and burn a full retry cycle (3 attempts x whatever the provider's timeout is) on a guaranteed failure. This also reduces noise for card 98's retry UI (fewer "no key" failures to retry) and pairs naturally with 134's proposed `assertCanStartJob` helper. Once 136's team-key resolution exists, extend this same check to look at team keys too.

## Superthread 121: Greyed-Out Models by Subscription Plan (backlog, light note)

No subscription/plan system exists yet - do not design one now. The extension point already exists structurally: `ProviderMeta` (`server/worker/providers/catalog.ts`) or each `ProviderModel` entry could gain an optional `minPlan?: string` later, checked client-side (grey out in `ModelSelector.vue`) and server-side (guard in `POST /api/jobs`, mirroring how `keyProviderId` is already threaded through both layers). Nothing to build until a plan/subscription concept exists.

## Superthread 122: Extended Provider Customization (backlog, light note)

Record-only for now. The [Provider API Audit](/backend/provider-api-audit) lists provider-specific optional parameters not currently exposed as UI controls per category (e.g. script: temperature/top_p/reasoning effort; image: style presets/seed/safety settings; audio: emotion/language controls; video: camera control/seed/cfg_scale). When this card is picked up, it's additive: extend the relevant job `input` shape and stage UI per provider, it doesn't require new architecture.
