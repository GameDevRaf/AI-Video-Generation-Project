Use this guide when adding or updating normal written docs. For Mermaid diagrams, also read [Diagrams](/guides/diagrams).

## Where docs live

Maintained docs live in `docs-site/content/`. Historical planning notes live in `docs-archive/` and are not maintained.

Use the Docus MCP server when it is running:

1. Call `list-pages` to find existing pages.
2. Call `get-page` for pages relevant to the task.
3. Edit the Markdown source in `docs-site/content/`.

If MCP is unavailable, inspect `docs-site/content/**` directly.

## Page structure

Every content page needs frontmatter:

```yaml
---
title: "Short Page Title"
description: "One sentence describing when this page is useful."
---
```

Keep titles short because Docus uses them in navigation, SEO, and MCP page listings. Descriptions should help agents decide whether to read the page.

## File and route conventions

Docus uses numeric prefixes for ordering. The prefix is stripped from the route.

```text
docs-site/content/5.guides/5.documentation.md -> /guides/documentation
docs-site/content/2.backend/4.api-routes.md   -> /backend/api-routes
```

When adding a page:

- Put it in the section where an agent would naturally look first.
- Use the next numeric prefix in that section.
- Add or update `.navigation.yml` only when creating a new section folder.
- Prefer updating an existing page over creating a near-duplicate page.

## Links

Use route-style links, not source-file links:

```md
[API Routes](/backend/api-routes)
[Add an API Route](/guides/add-an-api-route)
```

Do not link to `docs-site/content/...` paths from content pages. Preserve anchors when rewriting links.

## Writing style

Write for two audiences: a developer new to this codebase and an AI coding assistant trying to make safe edits.

- Keep pages practical and specific to this repo.
- Prefer examples, file paths, commands, and invariants over broad explanation.
- Do not duplicate architecture that already exists elsewhere; link to the better source.
- Keep action guides step-based and concise.
- Update docs in the same change as code, tests, or schema changes.
- Do not use em dashes. Use a colon, comma, parentheses, or a spaced hyphen instead.

## When to update docs

After every code change, check whether docs need updates:

- API behavior changed: update `/backend/api-routes` or `/guides/add-an-api-route`.
- Worker behavior changed: update `/backend/job-queue-and-worker` or `/backend/job-handlers`.
- Provider support changed: update `/backend/providers` and `/guides/add-a-provider`.
- Frontend workflow changed: update the relevant frontend page.
- Database shape or conventions changed: update `/database/schema` or `/database/conventions`.
- Common workflow lessons changed: update a guide rather than bloating `CLAUDE.md`.

Also check whether `/overview/diagrams` needs an update. If it does, read [Diagrams](/guides/diagrams) first.

## Validation

Use the fast preflight as the normal validation step for routine docs edits:

```bash
cd docs-site
npm run check
```

This catches the common cheap failures quickly: missing frontmatter, duplicate routes from filename prefixes, source-file links instead of route links, and unbalanced code fences.

Run the full static validation only occasionally: for larger docs-site changes, docs rendering/debugging work, or when you specifically need to verify the static site build end to end.

```bash
cd docs-site
npm run generate
```

If the docs server is running, spot-check changed routes in the browser and use MCP `list-pages` to confirm new pages appear.
