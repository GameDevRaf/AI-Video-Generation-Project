title: "Composables"
description: "Reusable frontend logic for provider state, jobs, projects, and media."
---

Reusable stateful functions in `app/composables/`, auto-imported everywhere. Unlike stores, **each call creates its own state** - two components calling `useScenes(id)` have independent scene lists (they stay consistent because both re-fetch from the server). The main exception is helpers that intentionally coordinate one workflow across components with `useState`, such as `useSceneOrderSync`.

A recurring parameter: `projectId: MaybeRef<string>` - accepts a plain string or a `ref`; internally read with `toValue(projectId)`. Callers pass `toRef(props, 'projectId')` so the composable stays correct if the prop changes.

---

## useJobPoller.ts - `useJobPoller()`

The standard way to run **one job at a time** and watch it finish. Used by every stage for single-job actions.

**Returns**
| Name | Type | Meaning |
|---|---|---|
| `job` | `Ref<JobWithOutputs \| null>` | Latest polled job, **including `job_outputs`** - components read results straight off this |
| `polling` | `Ref<boolean>` | Interval active |
| `isRunning` | `Computed<boolean>` | starting or polling or status queued/processing - bind buttons' `:disabled` to this |
| `isDone` / `isFailed` | `Computed<boolean>` | Terminal status checks |
| `error` | `Ref<string \| null>` | Submission/polling error |

### `startJob(projectId, type, input): Promise<JobWithOutputs | undefined>`
Guards against concurrent calls (returns immediately if one is running - double-click protection layered on top of the server-side dedup), POSTs `/api/jobs`, then polls `GET /api/jobs/:id` every 2 s (`useIntervalFn` from VueUse) until `completed`/`failed`.

### `retryJob(failedJobId, overrides?): Promise<JobWithOutputs | undefined>`
Manual retry: same re-entrancy guard and polling behavior as `startJob`, but POSTs to `` `/api/jobs/${failedJobId}/retry` `` instead of `/api/jobs`. The response is a **new** job (different id) reusing the failed job's own provider/model/input unless `overrides` is given; `job` starts tracking that new job immediately. Since there's no automatic retry anymore (see [Job Queue and Worker](/backend/job-queue-and-worker)), this is the only way to re-run a `failed` job.

Stages don't render `error` / `isFailed` inline anymore: on a `failed` job they route the failure to `useNotificationsStore()` (a persistent toast whose Retry calls `retryJob`), and `dismiss` it on success. See [Stores](/frontend/stores#notificationsts-usenotificationsstore) and the Retry-pattern note in [Components](/frontend/components).

### `reset(): void`
Stop polling, clear all state.

**Typical usage**: `watch(job, j => { if (j?.status === 'completed') refreshData() })`.

## useScenes.ts - `useScenes(projectId)`

Scene list + editing + the **timestamp recalculation** logic that keeps `start_time`/`end_time` consistent whenever order or durations change.

**State**: `scenes: Ref<DbScene[]>`, `loading`, `error`, computed `totalDuration` (sum of durations).

### `fetchScenes(): Promise<void>`
`GET /api/scenes?projectId=` into `scenes` (ordered by `order_index`). Also registers the fetched order as the saved baseline for `useSceneOrderSync` unless the Script tab currently has a pending unsaved reorder.

### `recalcTimestamps(list: DbScene[]): DbScene[]` *(pure)*
Walks the list in order, assigning `order_index = i` and cumulative `start_time`/`end_time` from durations (missing duration - 5 s). Returns a **new** array; does not touch state or the server. Exported so AudioStage can reuse it after audio generation changes durations.

### `persistTimestamps(list): Promise<void>`
`POST /api/scenes/reorder` with each scene's `{ id, order_index, start_time, end_time, duration }`. Always call this after `recalcTimestamps`. On success it marks that list as the new saved baseline for `useSceneOrderSync`.

### `updateScene(id, patch): Promise<void>`
Optimistic local merge. If `duration` changed - full recalc + persist of **all** scenes; otherwise a single `PATCH /api/scenes/:id`. `patch` may contain `script_text`, `title`, `duration`. If the Script tab already has a pending reorder, the duration path stages the recalculated list into `useSceneOrderSync` first so the flush persists both the final order and the new timings together.

### `moveScene(id, direction: 'up' | 'down'): Promise<void>`
Swap with the neighbor, recalc, then stage the new list in `useSceneOrderSync`. No-op at list edges. This is intentionally local-only until the user leaves the Script tab or the workspace route.

### `deleteScene(id): Promise<void>`
`DELETE` on the server first, then remove locally, recalc + persist the remainder. If a reorder was already pending, it flushes the updated post-delete order immediately so later tabs see the correct structure.

### `createScene(): Promise<DbScene>`
`POST /api/scenes` (empty scene appended server-side), append locally, recalc + persist. Returns the new scene. If a reorder was already pending, it flushes the updated list immediately after the new scene is inserted.

## useSceneOrderSync.ts - `useSceneOrderSync(projectId)`

Shared Script-tab workflow state for **deferred scene reordering**. Unlike `useScenes`, this composable intentionally uses `useState`, so the workspace page and SceneSplitStage both see the same pending reorder for one project.

**State**
| Name | Meaning |
|---|---|
| `hasPendingReorder` | `true` when the current local scene order differs from the last saved order |
| `flushing` | `true` while the page is persisting the pending reorder |

| Function | Behavior |
|---|---|
| `registerFetchedScenes(list)` | Saves the server order as the baseline unless a local reorder is already pending |
| `markPersistedScenes(list)` | Marks a just-persisted list as the new baseline and clears pending state |
| `stagePendingReorder(list)` | Stores the current local order snapshot if it differs from the baseline; clears pending state if the user reorders back to the original order |
| `flushPendingReorder()` | `POST /api/scenes/reorder` once, then best-effort `POST /api/audio/combine` so the combined `voice_track` follows the new order without re-running TTS. Missing per-scene audio is treated as a non-fatal no-op. |

## useImageStage.ts - `useImageStage(projectId)`

Owns the Image tab's data: prompts and generated images, both keyed by scene id.

**State** (all `Ref<Map<string, ...>>`):
- `prompts`: sceneId - `{ sceneId, outputId, prompt }` (outputId needed for saving edits)
- `images`: sceneId - image URL
- `generationPrompts`: sceneId - the prompt used when the current image was generated (staleness detection)
- `loading`

| Function | Behavior |
|---|---|
| `fetchPrompts()` | `GET /api/image-prompts` - `prompts` |
| `fetchImages()` | `GET /api/images` - `images` + `generationPrompts` |
| `savePrompt(sceneId, newText)` | Optimistic map update + `PATCH /api/image-prompts/:outputId` |
| `setPromptsFromJob(outputs)` | Replace the prompt map from a completed job's parsed outputs |
| `getPrompt(scene)` / `hasPrompt(scene)` / `getImage(scene)` / `getGenerationPrompt(scene)` | Per-scene readers (take a `DbScene`) |

---

## useVideoStage.ts - `useVideoStage(projectId)`

Mirror of useImageStage for the Video tab (`/api/video-prompts`, `/api/videos`). Differences: per-scene readers take a **sceneId string** (not a scene object), and it adds `hasAnyVideo` / `hasAnyPrompt` computed flags used to label buttons ("Generate" vs "Regenerate").

## useAudioStage.ts - `useAudioStage(projectId)`

Voice settings + the existing voice track. Also exports module-level constants:

- `VOICES: Record<'elevenlabs' | 'openai_tts', VoiceOption[]>` - static voice catalog (id, name, gender). Only these two providers have UI voice pickers; other TTS providers use handler-side defaults.
- Interfaces `VoiceOption`, `AudioSettings`.

**State**
| Name | Meaning |
|---|---|
| `settings: Ref<AudioSettings>` | `{ provider, voiceId, speed, stability, similarityBoost }` (stability/similarity are ElevenLabs-only) |
| `audioUrl: Ref<string \| null>` | Latest `voice_track` URL |
| `generationSnapshot` | Scene text snapshot stored when the track was combined - compared with current scenes to show the "stale audio" dot |
| `currentVoices` *(computed)* | Voice list for the selected provider |

| Function | Behavior |
|---|---|
| `fetchExistingAudio()` | `GET /api/audio` - `audioUrl` + `generationSnapshot` |
| `setAudioUrl(url)` | Direct setter (used after uploads) |
| `setProvider(p)` | Switch provider and reset `voiceId` to that provider's first voice |

Note: the actual generation orchestration (one job per scene, polling, combine call) lives in `AudioStage.vue`, not here - see [Components](/frontend/components#audiostagevue). The same `voice_track` combine route is also reused by `useSceneOrderSync` after deferred Script-tab reorders.
